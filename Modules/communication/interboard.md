# 共享 CAN / CAN FD 板间通信

## 配置与启用边界

同一路 CAN FD 可以同时服务 DM 的 8 字节 MIT 帧与另一块板的长帧。两者都使用 `CAN_<Fdcan>`，
由统一过滤器/实例表按标准 ID 分发；不存在板间模块独占总线或另占过滤器 0 的行为。
同一总线的 TX put-index/Message RAM 提交由短临界区串行保护，不等待空闲槽。

- `Core/Inc/board_can_config.h` 是 C/C++ 共用配置。上下板各有一张 CAN1/2/3 模式、过滤器数和时序表。
- CMake：`-DINFANTRY_BOARD_GIMBAL=1` 为云台板，`=0` 为底盘板，应用与外设初始化使用同一个角色。
- `INFANTRY_INTERBOARD_FDCAN` 在各板分支内选择本地 CAN 控制器；两端本地控制器编号可以不同，
  但必须连接到同一物理总线，并匹配帧格式、仲裁/数据波特率和 BRS。
- 默认映射保持原状：CAN1/2 经典、CAN3 FD+BRS，板间端口为 CAN2，`ENABLE_INTERBOARD=false`。
  这不是实物接线确认，不自动注册 DM、不启用任何电机。要让 DM 与板间共线，须先把选定的本板总线配置为 FD，
  并向 DM 初始化配置传入同一控制器句柄；确认后才开启板间模块。
- FD 后端容量为 64；DM 仍明确设置 `tx_len=8`，MIT 编解码量程仍需与电机固件匹配。
- 经典总线仅使用 classicCan 后端。FD 总线统一使用 Fdcan 后端；不支持在同一物理控制器上混用两套注册表。
- 队列、过滤器不足或注册 ID 重复时返回失败；应用必须检查 Init/Start 返回值。

## 外设与共享 RAM

`fdcan.c` 在每次 HAL 初始化前调用 `ApplyBoardCanConfiguration`：
经典元素为 8 字节、FD 元素为 64 字节；按各路实际元素数/大小连续计算 Message RAM 偏移，
不继续使用旧的 0x406/0x812 偏移。越过 H723 的共享 10KB RAM 范围会拒绝初始化。
默认三路总占用为 976 个 32 位字（3904 字节），其余总线模式改变时会重新计算。

保留了 CubeMX 生成的基础配置，板卡表是最终覆盖层。重新生成后必须保留 USER CODE 0 中的覆盖函数，
并在 CAN1/2/3 的 `HAL_FDCAN_Init` 前恢复对应的三个调用；CMake 会检查这些调用，缺失时停止配置，
不能忽略错误继续使用旧容量。实际时钟、时序和 CAN FD 收发器能力必须上板确认。

## 线路格式

云台→底盘使用 0x301，底盘→云台使用 0x302；与 DM 接收/反馈 ID 不得冲突。
每端最多注册 8 个发送主题和 8 个接收主题。主题号 1..255，0 保留心跳。

### CAN FD 单帧（新协议，两板须同步升级）

| 字节 | 含义 |
|---|---|
| 0 | 主题 ID；0为心跳 |
| 1 | 8 位消息序号，循环回绕 |
| 2 | 真实业务数据长度 0..60 |
| 3 | 协议版本标记 0xA1 |
| 4.. | 业务数据，剩余 DLC 补齐字节必须为零 |

业务消息长度 1..60；60 字节业务加 4 字节头正好是一帧 64 字节。
例如 48 字节业务的真实协议长度是 52，DLC 补齐为 64，但不会把剩余 12 字节发布给订阅者。
心跳为 `00 00 00 A1`，4 字节 FD 帧，不含业务负载。
FD 实际帧长采用合法的 0..8/12/16/20/24/32/48/64 编码，接收端校验版本、真实长度及补零。

### 经典 CAN 分片（兼容原有短消息格式）

第 0 字节为主题号，第 1 字节高 4 位为序号、低 4 位为分片号，后面最多 6 字节数据；
心跳仍为两字节 `00 00`。最大业务长度为 60（10片），既有≤48字节消息的格式不变。
接收端仅发布完整、连续、相邻分片间隔小于 50ms 的消息，错误片会丢弃当前重组。
新增长度超过48字节时，旧版本接收端不能直接使用，须同步升级。

## 时序、负载与失联

每100ms尝试发送心跳，300ms无有效对端链路帧即离线；时间按实际RTOS频率换算。
收到的数据用 ISR 到达 tick 标记，队列积压的过期帧不会刷新在线状态。未知主题或协议错误帧不续命。
心跳在线不等于某条底盘指令还有效；业务消息应携带源时间/序号，执行层单独检查超时并停机。

每2ms轮询，单轮最多发送2帧（含心跳），发送时至少保留2个TX FIFO槽给电机；
限制在实际入队临界区内复核，不是仅在任务外观察队列。
按主题轮转，经典长消息可跨多轮发送；50ms仍未发完则丢弃待发旧消息，不无限重试。
该策略不是硬实时带宽承诺，也不是总线功率管理：64字节帧开始发送后不能被高优先级电机帧中途抢占，
还须结合电机周期、总线利用率和 CAN ID 仲裁顺序做实测。

`LinkStatus` 发布在 `interboard/link`，含最近有效RX tick、收发计数、在线状态、
RX队列溢出/过期丢帧累计和TX入队失败累计；帧计数为16位，允许回绕。
队列满不会阻塞 ISR；某模块启动失败不会停止同路已工作的 DM 或 DJI 控制器。

## 应用使用

在调度器启动前先 `interboard::Start()`，再在两板注册相同主题号和固定长度，方向相反。
发送侧通过 `PubRegister/PubPushMessage` 发布，接收侧通过 `SubRegister/SubGetMessage` 读取。
例如两板共用3个float组成的12字节底盘命令，必须明确字段单位、字节序和结构布局，不直接依赖编译器填充。
消息中心是最新值邮箱，不提供可靠事件确认；单发等一次性事件需另有应用级确认/去重。

## 验证边界

已完成代码层共享路由、8/64字节容量、DLC/BRS、MIT适配、版本/长度校验、经典分片及调度实现。
验证使用真实CAN/DM/板间源文件与模拟HAL/RTOS，覆盖两种板卡角色、DM/板间两种注册顺序、
长帧边界/零填充、队列满、过期帧、TX入队失败、重复过滤器与不同BRS模式。
临时验证代码不加入固件或正式tests目录。

未烧录或验证实物：电机固件CAN FD设置、收发器能力、实际接线/波特率、实时抖动和总线负载仍需上板确认。
当前整工程另有底盘占位参数/通道定义缺失，通信目标文件编译通过不等于整车固件已可运行。
